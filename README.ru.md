# Артель

Фреймворк агентной разработки для одного разработчика и множества ИИ-агентов — от «открыл чат» до «продукт в проде», для всего от бота на выходные до клиентского продукта в проде. Быстро, экономно, без потери качества, независимо от провайдера моделей.

Статус: **0.3.1** — спецификация утверждена 04.10.2026 (0.2.1 — исправления по ревью сборки, см. `CHANGELOG.md`); десять скиллов со скриптами собраны и прогнаны на двух реальных проектах. Установка: `git clone https://github.com/mikeplotnikov/artel && artel/bin/install.sh`; как начать — `docs/quickstart.ru.md`.

Что нужно: Python 3.11+ (только стандартная библиотека), `git`, `gh`; желательно — источники документации в каждой оболочке (Context7, DeepWiki; `docs/adapters/`). Опциональные адаптеры: если они установлены, два шага скиллы отдают внешним скиллам и агентам — интервью и проверку спецификации (`user-spec-planning`) и ревью (`code-reviewer`, `test-reviewer`, `security-auditor`, `infrastructure-reviewer`, `layout-reviewer`, `documentation-reviewer`, `codex-reviewer`); замена секретов — `secret-handoff`. Совместимые `user-spec-planning` и первые шесть ревьюеров опубликованы в [molyanov-ai-dev](https://github.com/pavel-molyanov/molyanov-ai-dev) (MIT); `codex-reviewer` и `secret-handoff` в этот репозиторий не входят. Без адаптера шаг выполняется вручную по тем же правилам.

Что внутри:
- `docs/core.md` — методология: маршруты (новый продукт, изменение, инцидент, аудит, приём действующего проекта), уровни риска T0–T3, ворота владельца, роли, политика тестирования, защита, документация.
- `docs/contract.md` — какие возможности среды обязательны, как артель деградирует без остальных, проверки `artel doctor`.
- `docs/adapters/` — как артель работает в Orca, без оркестратора, на GitHub, в Claude Code и Codex.
- `skills/` — десять скиллов артели (вход — `artel`) со скриптами; ставит их `bin/install.sh`.
- `artel.toml.example` — личная конфигурация пользователя: провайдеры, подписки, оркестратор, хостинг кода; из неё генерируется матрица «роль → модель».
- `evidence/INDEX.md` — источники, на которых стоят правила.

Главные идеи:
1. Права у роли, а не у провайдера; ревьюер — из другого семейства моделей, чем автор.
2. Тяжесть процесса — по последствиям изменения, а не по типу файла.
3. Состояние — в файлах репозитория, а не в чате.
4. Жёсткие запреты — на стороне хостинга кода и CI, хуки агентов — только ограждение.
5. Сначала приёмочные тесты от другой сессии, потом проверка качества тестов запуском мутантов.
